Interviews — filtering and sorting, all three tabs

What this page is

A working prototype of the Interviews page on virtual.jobfairx.com/employer/#/interviews, covering all three tabs. Markup, tokens and spacing were read off the live DOM, not eyeballed.

All candidate data is the real Transdev data as of Sep 8 2026: Upcoming 21, Pending 1, Past 54 (26 interviewed plus 28 who missed the interview). Nothing is invented.

The existing layout does not move. Same header card, same three tabs, same cards, same columns. The Feedback pills on Past are the live component untouched — 32px tall, 106px min-width, 8px radius, 13px/600, dots #16a34a / #c2410c / #991b1b. Do not restyle them.

The rules

1. Two filter scopes, and they must not be mixed. Hiring event and Job are page-level: header card, right-aligned, and they apply to every tab and every card. Verified on the live app — selecting an event takes Upcoming, Pending and Past to (0) together.

Everything else is table-level and lives on its column header. Feedback and Interviewer only exist on Past › Interviewed candidates. Interview method only exists on Upcoming and Pending.
2. One control per column. Never both. A column either sorts (arrow on the label) or filters (funnel). No column opens a menu with a sort section and a filter section in it.
3. Controls are always visible. They never appear or disappear based on the data. An earlier pass hid a control when its column held a single value. On real data that hid almost everything, because every upcoming interview is the same job, same city, all Video. It is also unlike any comparable product: Ant Design declares filters per column and always shows them; AG Grid and Excel always open the column menu regardless of how many values it holds. An employer who learns "I filter method here" and later finds the control gone reads that as broken.

So the funnel renders even when it opens to one option. Today Interview method on Upcoming reads Video 21 and filtering to it changes nothing. That is correct.
4. The sort arrow is visible at rest. 50% opacity at rest, full on hover, blue with a bold label when sorted. IBM Carbon hides it until hover; we followed that at first and it produced header rows with nothing visible in them, so we dropped it.

Desired job carries no column control on any tab — it is filtered from the header card, because it applies to every table at once. Desired location, Notes and Action carry nothing.

Feedback does not sort. Four values over 26 rows: sorting Yes-first answers the same question as filtering but leaves the No rows on screen. The filter is strictly better, so the sort would be dead weight.

Timestamps sort, they do not filter. Filtering a timestamp needs a date-range picker, and the Hiring event filter already does that job. On Past, rows with several interviews (Bryant Mercely has three) sort on the first interview time.

A filter menu lists only the values present in the current scope. It does not pad the list with Phone 0 and In-Person 0 for methods this employer has never used.

Two features that are not filters

Upcoming groups by time slot. 21 interviews across 7 slots on one day. On event day the question is "who is in the next block", not "show me the Video ones". Slot subheaders carry the time and a candidate count, and the first group is tagged NEXT UP.

Grouping is the default and drops automatically when the user sorts, because a sorted list and a slot grouping contradict each other. Clearing the sort restores it.
Pending supports bulk actions. Every Pending row is a decision. With thirty requests the week of an event, the work is not finding them, it is clicking Accept thirty times. Checkbox column, select-all in the header, and a bar that appears on selection with Accept N and Decline N.

Select-all takes the filtered set, not the whole table. Bulk Decline must confirm before it fires — it is destructive and it messages the candidate. Bulk Accept can fire directly. The confirm step is not built in this prototype.

Interaction rules

  • Sort is three-state: ascending → descending → off. Off restores the table's default order.
  • One sort at a time per table. Past has two tables and they sort independently.
  • Filters are multi-select. "Yes and Maybe" is the shortlist question a recruiter actually asks; single-select cannot answer it. Nothing checked means no filter, so there is no "All" row.
  • A filter menu applies on each checkbox and stays open, so several values can be set in one pass. Clear is disabled when nothing is checked.
  • Filter counts rescope to the page-level filters and to the other column filter on the same table — checking an interviewer recounts the Feedback options against that interviewer's interviews only.
  • Applied filters show as a chip beside the card title; its × clears that column.
  • Card titles read (21 of 26) when filtered, plain (26) when not.
  • Tab counts stay absolute. Past always reads (54). A tab is a destination, not a result count — and if Past reflected the filter, Upcoming and Pending would have to as well.
  • Switching tabs clears column-level filters and sorts. Header card filters persist, because they are page-level.
  • An empty result renders the card's empty state, not a bare row.

Decided — do not reopen

  • Header filter height: 44px stacked, caption over value.
  • Sort and filter never share a column.
  • Feedback filters, it does not sort.
  • Filters are multi-select, not single-select.
  • Controls always render, regardless of how many values the column holds.
  • Tab counts do not react to filters.
  • Hiring event and Job stay page-level, in the header card.

What you need to decide

1. Filter state in the URL Recommend yes — query params, so a filtered view can be bookmarked and pasted to a teammate, e.g. #/interviews?tab=past&event=1842&feedback=yes,maybe. Multi-select means the value is a list, so pick a separator and hold to it. Do not persist across sessions; a filter someone forgot they set becomes a support ticket.
2. Client or server filtering 54 rows is fine client-side. If any tab paginates, filtering and sorting must move server-side — filtering one page of results is worse than not filtering at all. Menu counts are cross-scoped, which is a real query if it runs on the server. Tell us which you are building.
3. The "Not set" feedback state The live Feedback dropdown's first option is Select, meaning unrated. The filter calls it "Not set". Confirm the API returns null rather than an empty string or a default so the two agree. Transdev has zero unrated rows today, so this path is untested against real data.
4. What "sort off" returns to Sort is three-state, so the third click restores something. Confirm each table's default order server-side so "off" is defined rather than whatever order the response happened to arrive in.
5. Does Upcoming ever span more than one day? Every upcoming interview today is Sep 11, so slot grouping is one day deep. If a second event's interviews land in the same list, confirm whether you want the current shape ("Sep 11 · 11:00 AM" on each group header) or a day header with times nested beneath it.
6. Bulk size cap Is there a limit on how many Accepts can fire in one request? If it is a few hundred, say so and the UI will chunk them and show progress rather than hanging on one call.
7. Narrow viewports Not designed. The header row holds the title plus two 216px controls, and the tables are already wide. Needs a call on stacking versus horizontal scroll before this reaches anyone under roughly 1280px.

Three things to fix that are not UI

"Interview location" is the wrong column name. On the live app that column holds Video / Phone / In-Person, which is the interview method. Two columns to its left sits "Desired location", holding a city. Two similar names, unrelated contents. This prototype renames it Interview method. Rename it in the live app before building a filter labelled with the wrong noun.
All four hiring events are named "New Orleans Hiring Event", with no date. They are impossible to tell apart in the dropdown. Pick one on the live app and all three tabs go to (0), with no way to know which event you chose or why it is empty. This prototype appends the date so the filter is usable. The real fix is in the event label and is worth doing whether or not any of this filtering ships.
The Job filter does nothing for this account. All 76 rows across all three tabs are "Autonomous Vehicle Operator", and 25 of the 26 past interviews were run by Hali. Both controls are built and correct; they simply hold one value each on Transdev. Per rule 3 they still render.
