Notes for the developer

This page is the design reference for the Workable Candidates tab. Everything above the line is the screen as approved; the names, numbers and employers are samples. The build detail (webhook, resume storage, request matching, data fields, acceptance criteria) is in the Workable to JobFairX Resume Handoff brief.

Where it lives
A new entry in the admin's QUICK LINKS list, right after SMS Automations, labelled Workable Candidates. The NEW tag is optional and can come off after the first weeks. Its own page, not a section of Manage Candidates.
Who is listed
Every candidate Workable delivers for Simple Staffing's postings (applied, not recruiter-sourced), one row per application, whichever board they started on. Rows whose application had no resume file stay in the list with Resume shown as None. Default sort newest applied first, 20 per page, Previous / page numbers / Next as elsewhere in the admin.
Columns
Candidate: name and city; the name opens the candidate's detail (contact details, the resume, the Workable profile link, the texts sent, the request). Job · Employer. Interview: the job's interview date. Applied: date and time of the application, in the time zone the admin uses elsewhere. Source: where they came from, from Workable's referrer domain mapped to a name (indeed.com → Indeed, linkedin.com → LinkedIn, monster.com → Monster, ziprecruiter.com → ZipRecruiter, glassdoor.com → Glassdoor, Workable's own board → Workable board; anything else shows the domain). Indeed gets the blue chip, the others grey. Resume: the filename, opening the stored file; None when Workable had no file; Downloading, retry n in amber while the download job is still retrying. Texts: T1, T2, T3 chips from the existing text log, green when delivered, grey when not sent. Email (new, 20 Oct): the state with its time, Delivered in green, Bounced in amber, Skipped in grey with the reason (Indeed address, no address, no JobFairX job), None when nothing was sent; under a delivered email, two chips, Opened and Clicked, green when it happened, grey when not. Opened comes from SendGrid's open event; Clicked from the request page (the link carries the application's code, below). The detail drawer lists every event with its time. Requested: date and time of the interview request, linking to it; Not yet until then. Booked from (new, 20 Oct): which message the request came through: Email (blue), Text 1, Text 2 or Text 3; a dash until there is a request. No Via column (Scott, 20 Oct 2026): every row is from Workable and the page title says so.
Applied row and Day
Last 7 days, Last 30 days (default), Last 90 days and This year filter by the day they applied. Day is a single-day filter on the same field and is always visible: picking a day clears the range chips, and picking a chip clears the day. No Custom button, no date range.
Dropdown filters
Job, Employer, Interview (date), Source, Requested (Any / Yes / No), Resume (Any / Yes / No), Email (Any / Delivered / Opened / Clicked / Bounced / Skipped / Not sent; new, 20 Oct), Booked from (Any / Email / Text 1 / Text 2 / Text 3; new, 20 Oct), Country (All / US / CA), plus a search box for name, email or phone. Every stat, the table, By source and By week all count the same filtered rows, so one job or one employer shows its own conversion.
Stats block
Candidates: rows in the current filter, with how many have a resume. Emailed (new, 20 Oct): applicant emails delivered, with bounced and skipped counts under it. Email opened · clicked (new, 20 Oct): opened ÷ delivered and clicked ÷ delivered, with the counts under them; opened is approximate (mail apps that preload images count as an open), clicked is exact. Texted: Text 1 delivered. Eight tiles in two rows of four. Requested an interview, with the resume-source split (attached from Workable, uploaded, built, skipped; the spec's four values). Request rate: requested ÷ candidates, whole percent. Median time to request: minutes from the first message sent (the email, or Text 1 when no email went) to the request. Request followed: share of requests credited to each message, the same value the Booked from column shows per row. A request that comes through the email's link (the link carries the application's code, see below) is credited to the email; any other request is credited to the last text sent before it (T1, T2, T3). The tile leads with the email's share. The Hide stats / Show stats button collapses the block to bring the list up; remember the state per admin user.
Blue header row
The table header stays fixed at the top of the screen while the list scrolls (position: sticky; top: 0 on the header cells). No element between the table and the page's scroll container may have overflow hidden or auto, or the header will not stick; use overflow: clip where a clip is needed. On this page the header sticks to the top of the viewport; in the admin it sticks under whatever fixed bar the admin has.
By source and By week
By source: candidates, emailed (delivered), requested, requests credited to the email, the request rate (requested ÷ candidates, bar length = the rate), and the two per-channel rates: ÷ emailed = requested ÷ emails delivered, ÷ texted = requested ÷ Text 1 delivered. All = the totals. By week: a grey bar of candidates, a light-blue bar of emails delivered and a blue bar of requests per week, Monday to Sunday, request rate labelled above each; the current week is partial. Both read the same filtered rows as the table.
The email link and tracking
The link in the applicant email is the job's request link with the application's own code on the end, for example ?e=k7m2q9, six random characters that mean nothing on their own. When the request page loads with that code it records Clicked on the application and, if the person goes on to book, credits the request to the email and matches it to the row without needing the phone or email match. The texts are not affected: they keep the plain job link, with no code, as the texts spec says. SendGrid open tracking on, which adds the usual invisible image to the email and reports an open; count it once per application and treat it as approximate. SendGrid click tracking off: SendGrid would rewrite the link through a tracking domain, and the request page already records the click with the code, so the link reaches the applicant unchanged.
Email sending
Sent through SendGrid from scott@simplestaffing.co (Scott, 20 Oct 2026). simplestaffing.co already carries the SendGrid DKIM records s1 and s2 and a DMARC policy of reject, so a DKIM-aligned send passes; add include:sendgrid.net to the domain's SPF record as well so both checks pass. Record SendGrid's events (delivered, bounce, dropped, spam report) on the application row; they feed the Email column, the Emailed tile and the two conversion pages. Never send to an indeed.com or indeedemail.com address; those rows show Skipped.
SMS Indeed Conversion page
Three columns join the existing daily table (second screen above): Emailed, the applicant emails delivered that day, and Email clicked, the applicants who opened the email's link that day, both after Sent; and Started from email, the requests started that day from the email's link, after Started. Everything else on that page, including the abandoned-step table, stays as it is.
Not on this page
No Export CSV, no column chooser, no phone layout: the admin is used on desktop only (Scott, 18 Oct 2026). Replies to the email live in Scott's mailbox, not here.
