Developer notes

Interviews › Past — filtering and sorting

What this page is

A working prototype of the Past tab on virtual.jobfairx.com/employer/#/interviews. The markup, tokens and spacing were read off the live DOM, not eyeballed. Candidate data is the real Transdev data as of Sep 8 2026 (26 interviewed + 28 missed = 54).

Nothing about the existing layout moved. Same header card, same three tabs, same two result cards, same eight columns. The Feedback pills in the rows are the live component untouched — 32px tall, 106px min-width, 8px radius, 13px/600, dots #16a34a / #c2410c / #991b1b. Do not restyle them.

What was added

  1. Two page-level filters in the header card, right-aligned: Hiring event and Job. Replaces the single 340px "All hiring events" button that sat to the left of the title. Right-aligned matches Events and Analytics; left-aligned was the odd one out.
  2. Column-header controls on the two Past tables. A column is either sortable (arrow on the label) or filterable (funnel), never both; columns that do neither carry no control at all.
  3. Active-filter chips next to the card title, with an × to clear.

Scope rules — the important part

There are two filter scopes and they must not be mixed up.

Job stays in the header specifically because it hits both tables. A column caret can only filter its own table, so a Job caret on each table would give you two controls fighting over the same field.

Counts inside a column menu rescope to the current page-level filter. Pick the Aug 10 event and Feedback recounts to that event — it must never show 21 yeses that are no longer on screen.

Notes, Action——

Why Feedback does not also sort. Four values across 26 rows. Sorting Yes-first answers the same question as filtering but worse, because the nos are still on screen and you scroll past them. The filter is strictly better, so the sort is dead weight.

Why timestamps do not filter. Filtering a timestamp needs a date-range picker, and the Hiring event filter above already does that job better. Multi-interview rows (Bryant Mercely has three) sort on the first interview time.

Why it is built this way

These are not house preferences, they are the documented conventions:

  • A sortable header is a button; clicking it toggles direction and aria-sort reports ascending/descending — W3C ARIA APG. Set aria-sort on the active column and remove it from the previous one.
  • Sort arrow is hidden at rest, appears on hover, and persists when the column is sorted — three states, unsorted / ascending / descending — IBM Carbon.
  • Sort and filter are separate affordances; the filter is a funnel that highlights when applied — Ant Design Table.
  • Clicking a column header sorts ascending, clicking again reverses — Salesforce lightning-datatable.
  • Page-scope filtering lives outside the table, not in headers — Shopify Polaris IndexTable, Carbon (toolbar).

An up/down glyph in a column header means sort in every one of these. It must never filter.

Interaction rules

  • Sort is three-state. Click cycles ascending → descending → off. Off restores the table's default order.
  • One sort at a time per table. Sorting a different column clears the previous one.
  • Filters are multi-select. "Yes and Maybe" is the shortlist question a recruiter actually asks; single-select cannot answer it. Nothing checked = no filter.
  • Filter menu applies immediately on each checkbox and stays open, so several values can be set in one go. Clear is disabled when nothing is selected.
  • Filter counts rescope to the current page-level filter and to the other column filter — checking Nelson recounts the Feedback options against Nelson's interviews only.
  • States: sort arrow blue with the header label bold · funnel filled blue with a count badge of how many values are checked.
  • Chip next to the card title lists the applied values ("Feedback: Yes, Maybe"); its × clears that whole column.
  • Card title shows (23 of 26) when filtered, plain (26) when not.
  • Tab counts stay absolute. Past always reads (54). A tab is a destination, not a result count — and if Past reflected the filter, Upcoming and Pending would have to as well.
  • Empty result renders a full-width row: "No candidates match these filters."

Decided — do not reopen

  • Header filter height: 44px stacked. The prototype used to carry a 44px / 38px toggle; it is gone and 44px is the build. Caption over value, matching Analytics.
  • Sort and filter never share a column. One control per header.
  • Feedback has no sort. Filter only.
  • Filters are multi-select. Not single-select, not radio.
  • Tab counts do not react to filters. Past always reads (54).
  • Hiring event and Job stay at page level, in the header card, not on columns.

What you need to decide

1. Filter state in the URL Recommend yes — query params, so a filtered view can be bookmarked and pasted to a teammate. e.g. #/interviews?tab=past&event=1842&feedback=yes,maybe. Multi-select means the value is a list, so pick a separator and stick to it. Do not persist across sessions; a filter someone forgot they set is a support ticket.
2. Client or server filtering 54 rows is fine client-side. If Past ever paginates, filtering and sorting must move server-side — filtering one page of results is worse than not filtering at all. Tell us which you are building so the menu counts can be sourced correctly; they are cross-scoped (see Interaction rules) and that is a real query if it runs on the server.
3. The "Not set" feedback state The live Feedback dropdown's first option is Select, meaning unrated. The filter calls it "Not set". Confirm the API returns null (not an empty string or a default) so the two agree. Transdev has zero unrated today, so this path is untested against real data.
4. What "sort off" returns to Sort is three-state, so the third click has to restore something. Confirm the server's default order for this table — it looks like interview time descending — so "off" is a defined state and not just whatever order the last response happened to arrive in.
5. Narrow viewports Not designed yet. The header row holds the title plus two 216px controls, and the table is already wide. Needs a call on stacking vs horizontal scroll before this ships to anyone on a laptop under ~1280px.

Two data problems, not UI

Every hiring event has the same name. The live event dropdown lists four entries all reading "New Orleans Hiring Event" with no date. They are genuinely indistinguishable — you cannot pick the right one. This prototype appends the date ("New Orleans Hiring Event - Sep 3") so the filter is usable. The real fix is in the event label, and it is worth doing whether or not any of this filtering ships.
The Job filter does nothing for Transdev. All 54 rows are "Autonomous Vehicle Operator", and 25 of 26 interviews were run by Hali. Both filters are built and correct, they just have one option each on this account. Recommend hiding a filter when it would render a single option, rather than showing a dropdown that cannot change anything.

Deferred

  • Desired location filter — one value for every employer we have. Add the caret the day someone posts in two cities; the column config already supports it.
  • Search by name — overkill at 26 rows, necessary at 200. Goes in the card header, right-aligned, if it ships.
