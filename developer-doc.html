1Read this first

The product

JobFairX runs virtual hiring events. Employers register for an event, post jobs, and interview candidates on event day. The platform historically supported video interviews only. It now supports three interview methods: Video, Phone and In person.

Vocabulary — non-negotiable

JobFairX delivers pre-qualified, self-scheduled interviews on event day. Not applications. Not resumes in a database.

  • Candidates request interviews. They never “apply.”
  • An employer accepting a request schedules the interview.
  • Say Video when you mean the method. “Virtual” is no longer a synonym for JobFairX — it is one of three methods.
  • “Join” is video-only language. Never use it for phone or in person, and never in a string shared across methods.
  • The column and the concept are called Interview location. A physical address is an Interview address.

The design rules this was built under

  1. Reuse existing components. Do not invent new UI patterns. The Lobby and Interviews pages are the source of truth.
  2. Don't change video. The live app is already built for video. Every change is gated so video is untouched unless explicitly stated. Two deliberate exceptions are listed in §16.
  3. The verb describes what the employer does; the icon and the chip describe how. Two verbs across three methods — “Start interview” and “Call candidate.”
  4. Prefer one honest string over three conditional ones. Only branch copy when a single wording would be false for some method.
  5. Don't ship a promise the code doesn't keep. If copy says something happens, wire it.
The test to build against. An employer who has only ever run phone interviews should be able to use JobFairX for a month and never meet a word, icon, button, status or email that assumes a camera — and an employer who has only ever run video should not notice anything changed.

2Data model — required

The prototype fakes state because it is a static file. These are the four places where the production model must differ, and the first one is a real bug if you copy the prototype.

1. Notes must be keyed by candidate ID, not by name

The prototype stores NOTES[candidateName]. It works there because the seed names are unique. In production, two candidates who share a name would have their interview notes silently merged into one record. This is the single most important line in this document. Key notes by candidate ID.

2. Method is a field on the interview record

The prototype passes method as a URL parameter — ?method=video|phone|person — persisted in sessionStorage.jfxMethod and read through window.JFXM. That is scaffolding so a static file can demo three modes. In production:

  • The event carries a default method, set in Interview settings.
  • Each interview carries its own method, defaulting to the event's. Reschedule can change it for one interview without touching the others.
  • Because method lives on the interview, moving to per-job or per-interview selection later is a UI change, not a migration.

3. Third-party video is not a fourth method

It is a second field on video, which is already how Edit Post models it internally:

interview.method   : 'video' | 'phone' | 'person'
interview.videoMode: 'native' | 'third'      // video only
interview.meetingUrl: string                  // required when videoMode === 'third'
interview.address  : { street, suite, city, state, zip, parking, arrival }  // person only

The chip stays Video on every surface for both video modes. Only the payload line beneath it differs. Do not add a fourth chip, a fourth icon or a fourth colour.

4. Notes must persist

In the prototype notes live in memory and a reload clears them. Real persistence is required — a note taken mid-interview must survive into the Interviewed tab, the candidate drawer, and any later session.

3Where the method comes from

LevelSet whereRule
Event defaultInterview settings, in Edit Post and Setup FlowApplies to every interview scheduled for that event unless the interview overrides it.
Per interviewThe schedule / reschedule modal's Format pickerOverrides the event default for that one interview. Always wins.

Changing an event's method after publication

The employer is offered one decision for the whole confirmed batch, not per candidate:

  • Keep confirmed candidates on their original method — legitimately produces a mixed event.
  • Move everyone and notify them.

Mixed events are real and supported. Every list that spans events must render method per row.

The A/V test link is conditional

“Test your audio and video before your event” renders only when an upcoming event uses JobFairX video. It was previously permanent and account-level, so a phone-only employer was nagged forever to test hardware they never use.

Interviews tab built

Columns: Name | Desired job | Desired location | Interview time | Interview location | Action.

This is the one view that genuinely mixes methods — interviews across all events, on three tabs (Upcoming / Pending / Past). The Interview location column is unconditional: it renders even on a single-method programme. A column that appears and disappears depending on whether an event happens to be mixed is more confusing than one that is simply always there.

Note that Desired location (where the candidate wants to work) and Interview location (how the interview happens) both appear in this header row. That is intended and was decided knowingly.

Candidates tab built

Candidate-centric, filterable by stage. The method chip appends to the existing stage · time line beneath each candidate's name in the All view — it reuses that slot rather than adding a column. Method derives from the candidate's first interview event.

In the candidate drawer: the no-show reason line is method-aware (§12), and the primary action for a candidate scheduled today uses the method icon rather than always the camcorder.

5The lobby

Event header built

A line under the date range: method chip plus a description. It renders for all three methods. In person adds a Parking & arrival link opening a modal with the address, parking and arrival instructions — the first place the employer can read back what they typed into Edit Post.

For third-party video this line is where the meeting URL and Copy link belong. spec only

Waiting to interview — two sections built

Do not merge these. The split is not video presence detection. It is the arrival model, and it means the same thing for every method.
SectionMeaningRow carries
Interview roomsCandidate is present and actionable. Status Ready.The primary action — Start interview for video and in person, Call candidate for phone.
Waiting roomsCandidate is checked in but not yet actionable. Status Awaiting available interviewer.A kebab, on phone and in person only.

The Waiting-rooms kebab is not a convenience

Nothing detects that a phone or in-person candidate has left. This menu is the only way they ever exit that section without being interviewed.

  • Interview next — in person only. Pulls someone forward out of queue order, because the physical queue and the system queue drift apart.
  • Mark as interviewed — records an interview the app never observed. Requires an interviewer and an actual time; the confirm button stays disabled until both are valid.
  • Didn't show — the manual no-show.

Status normalisation

“Entering interview room” describes a video transition and nothing else. For phone and in person those rows read Awaiting available interviewer.

Interviewing tab built

Columns: Name | Desired job | Desired location | Interview location | Interview time | Interview duration | Interviewer | Notes | Action.

MethodAction group
Video[ Rejoin | End interview ]
Phone[ Call again | End interview ] — “Call again” replaces Rejoin. Different action, real use case, styled secondary.

The Notes column renders for phone and in person only, between Interviewer and Action.

Your status — video only built

The Your status: Available / Away control in the live lobby header, and the “Ready to start interviewing?” card it drives, render for video only.

Rationale, because it will look like an omission otherwise: phone and in person have no promotion event for an availability flag to gate. The candidate checks in, lands in Waiting rooms, and the next thing that happens is physical — the recruiter walks out and collects them, or dials them. Nothing is pushed to the candidate either way, so a self-reported availability flag has no job on those methods.

6Phone specifics

The Call panel built

An anchored popover, deliberately not a modal, so the queue stays visible while dialling. Contents:

  • Candidate name and role.
  • The phone number, large and selectable, with a Copy button and a tel: link.
  • The line: “Call {first name} from your phone. JobFairX doesn't place the call — candidates see the number you call from.”
  • The scheduled time.
  • I've started the interview (primary), No answer, Close, and Number looks wrong? which opens the message composer.
Opening the panel changes nothing. Only the explicit I've started the interview moves the candidate to Interviewing. Employers open this to copy a number, to check it, or after a voicemail. Opening a panel is not evidence an interview began.

No answer is two-strike

First press returns the candidate to the queue with a “No answer · N attempts” sub-line and flips the button label to Call again. Second press offers Mark as no-show. Employers routinely call twice; a one-strike rule would misreport reachable candidates as unreachable.

7In-person specifics

  • Start interview moves state in place. No new window, no modal.
  • Interview next on the Waiting-rooms kebab pulls a candidate forward out of order.
  • Mark as interviewed records an interview the platform never saw.
  • The Parking & arrival modal in the lobby header surfaces the address, parking instructions and arrival instructions captured in Edit Post.
  • The schedule modal blocks Send until street, city, state and ZIP are complete.

8Notes

Video takes notes inside the interview room. Phone and in person never open that room, so before this work their only surface was the Interviewed tab — after the interview had ended.

  • A Notes column on the Interviewing tab (phone and in person) opens the resume modal with the notes panel focused.
  • The resume modal widens to 1040px with a 340px notes panel on the right. Below 1100px the panel collapses into Resume / Notes tabs.
  • Side-by-side is the primary layout because simultaneity is the entire point — tabs alone would reduce clicks without letting you see both.
  • Video is untouched: no panel, no tabs, modal stays 680px.
  • The small notes modal is kept for the Interviewed tab — a quick after-the-fact edit doesn't need the resume.

Resume modal header was reduced from 178px to 79px, taking resume visibility from 60% to 82%. Scoped so it can only reach phone and in person.

9Ending an interview

End interview → “Have you finished interviewing {name}?” → two options.

AnswerResult
YesRow moves to Interviewed with the rating on the Feedback chip, the interviewer, the actual time, and the note on the Notes button. Tab counts follow.
NoCandidate goes back to Waiting rooms.

The evaluation modal pre-fills from the candidate's existing note, relabelled Interview notes, with a line saying where it came from. Do not blank the notes field when opening the evaluation — that destroys notes taken during the interview.

Ratings are Yes / Maybe / No. JobFairX does not track hires; the recruiter's rating is the outcome measure, so yes + maybe + no = completed in every analytics scope.

Two columns. Left (grey): a Format segmented control — Video / Phone / In-Person — the format's own fields underneath, then Message. Right (white): Interview Date, Start Time, Suggest multiple times.

  • One format applies to the whole proposal, not per suggested slot.
  • Send is blocked until in-person address fields are complete.
  • The modal holds one fixed size across all three formats — measured at top 40px, height 592px. The left column scrolls when in-person overflows. Do not let the box resize when the format changes.

11Edit Post & Setup Flow

  • Both contain the interview method picker — a segmented Video / Phone / In-Person control with per-method fields.
  • Video reveals JobFairX video call or Third-party video conferencing with a required Meeting URL, validated as https://.
  • In person reveals the full address set with completeness validation.
  • Edit Post carries the change-method modal — keep confirmed candidates, or move everyone.
  • Setup Flow's review page shows an Interview location row. It previously omitted the setting entirely, which meant the last screen before publishing hid the field with the highest cost of being wrong.

Writing conventions

Sound human. Casual-confident. No AI phrases. Buttons name the action, not the channel. Errors say what went wrong and how to fix it. Empty states say what to do next, not what to wait for.

Why one chip colour. Colour in this app means state — success, warning, danger, ready. The three per-method hues had borrowed those palettes for a dimension that carries no state at all: phone read as “good”, in person as “caution”, video as “ready”, and each collided exactly with an existing status colour. The icon carries the method now; the hue says nothing. Status badges were not changed, including No answer.

Geometry

  • Radius: 8px buttons, 10–12px inputs, 12px cards, 14px modals.
  • Buttons: primary blue filled; outline 1px solid #d4d2d0 on white. Height 36px in rows, 44px in forms.
  • Inputs 42–44px. Focus: border-color:#0044b3 plus 0 0 0 3px rgba(0,68,179,.12).
  • Cards: #fff, 1px solid #d4d2d0, radius 12px. Table cells 14px padding.
  • Badges: 3px 8px, radius 12px, 12px/500, white-space:nowrap.
  • Shadows: modals 0 8px 32px rgba(0,0,0,.2); popovers 0 8px 28px rgba(0,0,0,.16); menus 0 4px 16px rgba(0,0,0,.12).
  • Icons: 24×24 viewBox, fill:none; stroke:currentColor; stroke-width:2, round caps and joins.

The two deliberate video-facing changes

Everything else leaves video byte-identical. These two do not, on purpose:

  1. A video-only event now carries an Interview location column on the Interviewing tab, reading “Video” on every row. Consistency was chosen over density.
  2. The video method chip changed from blue to the shared chip treatment.

Two pre-existing conditions, noted so you don't chase them

  • Both dashboards carry a +2 raw div imbalance and Setup Flow +1. Present before this work, unchanged by it, most likely the counter matching <div inside JS template strings rather than a real defect.
  • Lobby rows print PDT inside a CT event. Pre-existing seed inconsistency; in person makes it indefensible.
Verification standard used throughout. Static checks are not sufficient — two bugs in this programme passed balanced-tag and syntax validation because the code was valid, just wrong. Every change here was loaded in a browser and asserted against the real DOM, then regression-checked against a clean copy of the previous commit: pixel-identical where video was meant to be untouched, and a full computed-style diff across every element where it was not.
