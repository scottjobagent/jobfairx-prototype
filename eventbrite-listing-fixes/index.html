19 published US listings: what was wrong, what is fixed, what is left

Three errors came from copying the Dallas draft. All three are now fixed on the live listings, and the two drafts that copies are made from are fixed too. The last part of this page is how to stop the errors when events are added through the Eventbrite API.

What is done

1

Confirmation page and email Fixed on all 19

Was: every listing thanked the buyer for reserving “the Dallas Job Fair on Wednesday, November 18, 11 AM to 3 PM Central”.

Now: each listing names its own city, day and time zone, in both the page message and the email message. Eventbrite confirmed each save and each one was read back.

2

Five-step picture Fixed on all 19 and on the Burlington draft

Was: the Dallas picture on every listing. Every candidate’s location read Dallas, and the interview card read Central Time (CST), Wednesday, November 18, 2026.

Now: one picture with no city and no date. The location column reads “Your city”. The interview card reads “Local time” and “Event day”, with no time zone letters. The same picture is on the Burlington (Canada) draft, which is still a draft.

3

Early registration discount Added on the 7 that are 30 or more days out

Was: no discount on any listing, so no green “Discounts applied” bar.

Now: $100 off all tickets on Houston, New York City, Brooklyn, Queens, Columbus, San Diego and Phoenix. Each shows the green bar and “From $406.87”. Each discount ends by itself at 11:59 PM local time on the day the event is 30 days out. The other twelve are inside 30 days, so full price is right.

4

The two drafts that copies are made from Fixed, both still drafts

Was: the Dallas draft (event 2003298293122) and the Las Vegas draft (event 2003266074756) each carried their own city picture and their own city’s confirmation wording.

Now: both have the picture with no city or date. The first line of both confirmation messages is placeholders: “Thank you for reserving your spot at the {{CITY}} Job Fair on {{WEEKDAY}}, {{DATE}}, 11 AM to 3 PM {{TIMEZONE}}.” A copy that is not filled in is now obvious.

5

Los Angeles time zone Fixed

Was: America/Vancouver. Now: America/Los_Angeles. Same date and time (Mon Oct 19, 11 AM to 3 PM), and ticket sales still end at 11 AM. Eventbrite offered to email attendees about the change. No email was sent.

It is still dated Fri Oct 30, 2026 and its top text still says Las Vegas, but its confirmation now has placeholders. If it is ever published as a real Las Vegas event, the first line has to go back to “Las Vegas Job Fair on Friday, October 30, 11 AM to 3 PM Pacific” first.

Burlington is still a draft Scott’s review

Event 2003313278945 has the new picture. It waits on Scott’s review and his word to publish.

How to prevent these errors in the Eventbrite API run

Why it happened: a copy carries everything the source draft has, including its picture and its confirmation wording, and it does not carry the discount. The title, date, venue, top text and job seeker link were changed on the 19. The picture, the confirmation wording and the discount were not.

Rule 1

Keep the template clean. It was fixed on 13 October

  • The template now has the picture with no city and no date, so every copy starts with a picture that is right everywhere.
  • Keep city, date and time zone out of every picture. A script cannot read a picture, so it cannot catch a wrong one.
  • Anything that changes per event sits in the template as a placeholder, never as a real city or date. A real city in the template is how Dallas ended up on 19 listings.
  • A copy does not carry a discount, and each event needs its own end date, so the discount is always added per event.
Rule 2

Set every per-event field on every copy. Do not trust what the copy carried

Confirmation wording. The page message is confirmation_message in ticket buyer settings. The reference has a second text, instructions. Check on one event which field feeds the email, then set both. The first line in the template is “Thank you for reserving your spot at the {{CITY}} Job Fair on {{WEEKDAY}}, {{DATE}}, 11 AM to 3 PM {{TIMEZONE}}.” Fill it like this: Phoenix, Wednesday, November 18, Mountain. {{TIMEZONE}} is one word: Eastern, Central, Mountain or Pacific. The other three paragraphs do not change.

Description. Eventbrite’s description is insert only and versioned. Every change resends all modules with the next version number, and it is not public until it is sent with publish true.

Discount. A starting point from Eventbrite’s API reference, not yet proven on this account:

POST /v3/organizations/{organization_id}/discounts/
{ "discount": {
    "type": "public",
    "amount_off": "100.00",
    "event_id": "<event id>",
    "quantity_available": 0,
    "end_date": "2026-10-19T23:59:00"
} }
  • event_id with no ticket list means all tickets. quantity_available 0 means unlimited.
  • end_date is the event’s own local time, written without a time zone: the event date minus 30 days at 23:59.
  • Test first. The reference lists four kinds (public, coded, access, hold). The one made on the Promotions screen is a newer automatic kind: it is named AutomaticDiscount_ and a number, and it read back earlier as type “open”, which the reference does not list. Create one by API on a single test event and look at the listing. If it shows the green “Discounts applied” bar, use it for the run. If not, the discounts have to be added on the Promotions screen.
  • Eventbrite allows one discount per event. Once a discount has ended, a new one cannot be added. The old one is edited and its end date moved.
Rule 3

Check every event by script, and publish only when every check passes

  • Read back each field in the table above and compare it with what that event should have.
  • Leftover placeholder scan. If the title, description, job seeker link or either confirmation message still has {{ or }} or __EVENT_SLUG__ in it, stop.
  • Wrong-city scan. Search the event’s title, description, ticket text and confirmation text for the template’s own words: its city, its date, its time zone. If any appear on an event that is not that city or date, stop.
  • Check the copy itself. A copy can fail partway and still leave a draft behind. Confirm the tickets, the payment setup and the description are all there.
  • If any check fails, leave the event as a draft and write it to the log. Publish with POST /events/{event_id}/publish/ only after a clean check.
Rule 4

Run five first, look at them, then run the rest

  • Publish five events. Open each public page, press Read more, and check the price line and the picture.
  • Public listing pages are cached for about five minutes, and an old copy can show once more after that. Reload before judging a change.
  • Keep a log per event: event id, city, date, what was set, and the result of each check.
